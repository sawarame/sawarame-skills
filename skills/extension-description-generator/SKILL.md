# Store Description & Permissions Justification Generator

## 概要
このスキルは、高品質でプロフェッショナルな Chrome ウェブストア用説明文および審査提出用の権限使用理由（Permission Justification）の自動生成を可能にします。
- **ストア説明文**: プロジェクト内の `_locales` ディレクトリ（`package/_locales/` を最優先）から判定した対応言語（見つからない場合は英語・日本語、ユーザーから明示指定がある場合はその言語）ごとに一貫性を保ちながら、主要な機能、技術的な利点、およびユーザーのメリットを言語別ファイル（`store_description.<lang>.md`）として出力します。
- **権限の使用理由**: `manifest.json` の権限宣言と実際のソースコードの実装に基づき、Chrome ウェブストアのプライバシー審査に必要な権限使用理由を `store_permissions_justification.md`（英語［審査提出用］・日本語［確認用］併記）として出力します。

### 出力ファイル一覧
デフォルトでは、プロジェクト内の `_locales` から自動判定した対象言語の `store_description.<lang>.md` および `store_permissions_justification.md` をプロジェクトのルートディレクトリに生成・更新します。
`<lang>` には、有効な言語フォルダ名のアンダースコア（`_`）をハイフン（`-`）に変換した識別子を使用します。
ユーザーが「特定の言語のみ」「説明文のみ」「権限の使用理由のみ」を明示的に指定した場合は、`_locales` による自動判定よりユーザーの指定を優先し、指定されたファイルのみを対象とします。

| 用途 / 言語 | 出力ファイル名 | 備考 / `_locales` フォルダ名との対応例 |
| :--- | :--- | :--- |
| 説明文（動的言語対応） | `store_description.<lang>.md` | `_locales/<locale>/messages.json` が存在する全言語を対象とし、`_` を `-` に変換（例: `en` → `store_description.en.md`、`en_US` → `store_description.en-US.md`、`ja` → `store_description.ja.md`、`zh_CN` → `store_description.zh-CN.md`、`zh_TW` → `store_description.zh-TW.md`、`ko` → `store_description.ko.md`、`fr` → `store_description.fr.md`）。`_locales` が見つからない場合は `en`・`ja` の 2 言語にフォールバック |
| 権限の使用理由 | `store_permissions_justification.md` | 審査提出用（英語＋確認用日本語を併記） |

## ガイドライン

### 1. 情報の収集と対象言語の自動判定
説明文や権限の使用理由を生成する前に、必ず以下の対象言語判定とファイル分析を行ってください。

#### 1.0 対象言語の自動判定ルール
1. **ユーザーによる明示指定の優先**:
   - ユーザーから特定の言語が明示的に指定された場合（例: 「日本語版だけ更新して」「韓国語のみ作成して」など）は、`_locales` による自動判定より **ユーザーの指定を優先し、指定された言語のファイルのみ** を作成・更新してください。
2. **`_locales` ディレクトリの探索優先順位**:
   - **最優先**: `package/_locales/` を確認します（`extension-skeleton-generator` の標準構成に準拠）。
   - **フォールバック探索**: `package/_locales/` が存在しない場合は、プロジェクト内の一般的な `_locales` 配置（プロジェクトルート直下の `_locales/`、`public/_locales/`、`src/_locales/` など、`manifest.json` と同じ階層またはパッケージ出力元の `_locales/`）を探索します。
   - **既定のフォールバック**: いずれの場所にも `_locales` ディレクトリが存在しない、または有効な言語フォルダが 1 つも存在しない場合は、既定のフォールバックとして **英語（`en`）と日本語（`ja`）** の 2 言語を対象とします。
3. **有効な言語フォルダの判定と命名規則**:
   - 検出した `_locales/` 直下のサブディレクトリのうち、中に `messages.json` が存在するフォルダのみを有効な対応言語として扱います（`messages.json` のない空フォルダや、`.DS_Store` などの隠しファイル・隠しディレクトリは無視します）。
   - 有効な言語フォルダすべてを対象とし、フォルダ名のアンダースコア（`_`）をハイフン（`-`）に変換した `<lang>` を用いて、プロジェクトルートに `store_description.<lang>.md` を生成・更新します。
     - 例: `en` → `store_description.en.md`、`en_US` → `store_description.en-US.md`、`ja` → `store_description.ja.md`、`zh_CN` → `store_description.zh-CN.md`、`zh_TW` → `store_description.zh-TW.md`、`ko` → `store_description.ko.md`、`fr` → `store_description.fr.md`

#### 収集対象ファイル
- `_locales/*/messages.json`: 対象言語の判定に加え、可能であれば各 `messages.json` に記載されている拡張機能名や説明文も情報収集の対象に含め、表記の一貫性を保ちます。
- `manifest.json`: 拡張機能名、バージョン、オムニボックスのキーワード、および権限関連フィールド（`permissions`、`optional_permissions`、`host_permissions`、`optional_host_permissions`、`content_scripts[].matches`、`externally_connectable`、`web_accessible_resources`、`content_security_policy` など）を確認します。
- `package.json`: プロジェクト名、説明、依存関係を確認します。
- `src/` または `js/` ディレクトリ: 実際の挙動や機能、各権限に対応する Chrome API 呼び出し（例: `chrome.storage.*`, `chrome.tabs.*`, `chrome.scripting.*`, `chrome.contextMenus.*` 等）、外部通信やリモートコードの有無を確認します。
- **プロジェクトの仕様書（仕様駆動開発フレームワークを含む）**: プロジェクトの目的、ターゲットユーザー、主要機能や差別化ポイントを正確に把握するために確認します。
  - **Spec Kit (`spec-kit`)**: `specs/*/spec.md`（機能要件・ユーザーストーリー）、`.specify/memory/constitution.md`（基本原則）など
  - **Kiro / `cc-sdd`**: `.kiro/steering/product.md`（プロダクト概要・コアバリュー）、`.kiro/specs/*/requirements.md`・`design.md` など
  - **OpenSpec**: `openspec/specs/` 配下の仕様書、`openspec/changes/` 配下の変更提案など
  - **その他のフレームワーク / 一般的な仕様書**: 各フレームワーク固有の仕様ドキュメント、または `SPEC.md`、`docs/spec.md`、`docs/specs/` など
- **GitHub Issue / PR（必要に応じて）**: ローカルの仕様書やコミット差分だけでは機能の詳細・背景・ユーザーメリットが十分に把握できない場合や、コミット履歴・ユーザー指示に関連する Issue / PR がある場合は、`gh issue view` / `gh issue list` / `gh pr view` / `gh pr list`（または GitHub MCP ツール）で内容やコメントを読み取ります（取得できない環境ではローカル情報のみで続行してください）。
- 既存の `store_description.<lang>.md`（および旧形式の単一ファイル `store_description.md`）、`store_permissions_justification.md`: トーン、スタイル、既存のフォーマットや記載内容を維持するために参照します。

#### 1.1 既存の言語別ファイル（`store_description.<lang>.md`）または `store_permissions_justification.md` が存在する場合
既存ファイルが存在する場合は、セクション 1.0 で決定した対象ファイルについて下記の手順で更新内容を分析し、必要に応じて更新してください。
1. 対象となる各既存ファイルについて `git log -1 <ファイル名>` を実行し、最後に更新されたコミットを特定します。
2. `git log <最後の更新コミット>..HEAD` を実行して、最後の更新以降のコミット履歴を取得します。
3. コミット履歴、`manifest.json` や `_locales/*/messages.json`・ソースコードの差分、上記の仕様書、および必要に応じて関連する GitHub Issue / PR の内容を分析して、既存ファイルの内容と照らし合わせます。
4. 未反映の新機能・変更点や権限の追加・削除・用途変更があれば、各対象ファイルを更新してください。また、対象言語のうち `store_description.<lang>.md` が未作成のものがある場合は、他ファイルと一貫性を保ちつつ新規作成してください（ユーザーから特定言語のみ指定された場合を除く）。
5. **現在の対象言語に含まれない既存ファイルがある場合**: プロジェクトルートに既存の `store_description.<lang>.md` が存在し、現在の `_locales` 判定結果に含まれない言語のファイルがある場合は、自動で削除しないでください（ユーザーが特定言語のみ更新を指定した場合を除く）。対象外（未更新）である旨をユーザーに報告し、削除してよいか確認してください。
6. 最後に、各ファイルの変更内容（および対象外ファイルの有無）をユーザーに説明してください。

#### 1.2 旧形式の単一ファイル（`store_description.md`）のみが存在する場合
既存のプロジェクトに旧形式の単一ファイル `store_description.md` のみが存在する場合は、以下の手順で言語別ファイルへ移行してください。
1. `git log -1 store_description.md` と `git log <最後の更新コミット>..HEAD` を実行して、`store_description.md` の最終更新以降のコミット履歴を取得します。
2. 既存の `store_description.md` に含まれている内容（トーン、構成、記載済みの機能）をベースとし、コミット履歴・仕様書および必要に応じて関連する GitHub Issue / PR の最新内容も反映したうえで、**セクション 1.0 で判定した必要な言語（`_locales` 内の有効な言語、見つからない場合は英語 `en`・日本語 `ja`、ユーザーから明示指定がある場合はその言語）の `store_description.<lang>.md` のみ**を新規作成します（必要に応じて `store_permissions_justification.md` もあわせて作成・更新します）。
3. 作成した各ファイルの内容と反映した変更点をユーザーに説明し、旧ファイル `store_description.md` を削除してよいかユーザーに確認してください（ユーザーの承認なく自動削除しないでください）。

#### 1.3 既存ファイルが存在しない場合
ユーザーに新規作成するかどうか確認してください（ユーザーから明示的に作成指示がある場合はそのまま作成して構いません）。新規作成する場合は、上記の情報を基にセクション 1.0 で判定した対象ファイルを生成してください。
1. `manifest.json`、`package.json`、および各 `_locales/*/messages.json` から名前、バージョン、主要なキーワード、および要求している権限一覧を抽出します。
2. プロジェクト内に仕様書（Spec Kit の `specs/*/spec.md`、Kiro / `cc-sdd` の `.kiro/steering/product.md` や `.kiro/specs/*/requirements.md`、OpenSpec の `openspec/specs/`、または `SPEC.md` / `docs/spec.md` など）が存在する場合は、その内容を参照して説明文や用途説明の内容を充実させてください。また、仕様や機能要件が GitHub Issue / PR に記載されている場合は、必要に応じてそれらも読み取って反映してください。
3. その他、ソースコードや既存のドキュメントから、拡張機能の機能および各権限の具体的な使用箇所を抽出して反映させてください。
4. 生成した内容を各対象言語の `store_description.<lang>.md` および `store_permissions_justification.md` に保存し、ユーザーに提示してください。必要に応じて修正の提案を行ってください。

### 2. コンテンツ構造
各言語ファイル（1ファイルにつき1言語のみ記述）は、以下の標準的な構造に従う必要があります：

- **名前 (`Name`)**: 拡張機能の正式名称。
- **短い説明 (`Short Description`)**: 簡潔で印象的な1文の要約（Chrome ウェブストアでは各言語とも最大132文字）。
- **詳細説明 (`Detailed Description`)**:
    - **目的**: 拡張機能の目的の簡潔な概要。
    - **主な機能**: 主要な機能の箇条書きリスト。
    - **特徴的な機能**: 他の似たようなアプリや機能との差別化ポイント。
    - **使用方法**: ステップバイステップの使用方法。
    - **開発者/上級者向け機能**: 技術的なメリットがあれば記載。

プライバシーポリシーについては別途URLを提供することが推奨されますので、説明する必要はありません。
既にプライバシーポリシーの説明が存在する場合は、削除してください。

### 3. 言語要件
従来の 5 言語には以下の詳細な言語・文体ガイドラインを引き続き適用し、それ以外の言語についても下記の共通品質ガイドラインに従って生成してください。

- **英語 (`en` / `en-*`: 例 `store_description.en.md`, `store_description.en-US.md`)**: プロフェッショナルで魅力的な、分かりやすい英語（特に指定や地域コードがない場合はアメリカ英語、地域コードがある場合はその地域の自然な表記）を使用します。
- **日本語 (`ja`: `store_description.ja.md`)**: 開発者や技術に詳しいユーザーに適した、自然で丁寧（です・ます調）かつ現代的な日本語を使用します。用語が一般的な日本の技術用語と一致していることを確認してください。
- **中国語・簡体字 (`zh-CN`: `store_description.zh-CN.md`)**: 中国本土のユーザーに適した、自然でプロフェッショナルな簡体字中国語を使用します。IT・ブラウザ拡張機能分野で一般的な簡体字の専門用語（例：`扩展程序`、`快捷键`、`标签页`、`书签` など）を用い、直訳調にならないようローカライズしてください。
- **中国語・繁体字 (`zh-TW`: `store_description.zh-TW.md`)**: 台湾を中心とした繁体字圏のユーザーに適した、自然でプロフェッショナルな繁体字中国語を使用します。簡体字からの単純な字形変換は避け、繁体字圏で一般的な IT 用語（例：`擴充功能`、`快捷鍵`、`分頁`、`書籤` など）を使用してください。
- **韓国語 (`ko`: `store_description.ko.md`)**: 開発者や技術に詳しいユーザーに適した、自然で丁寧な韓国語（文体は `합니다` 体で統一することを推奨）を使用します。韓国で一般的な IT・ブラウザ用語（例：`확장 프로그램`、`단축키`、`탭`、`북마크` など）を用い、自然な表現にローカライズしてください。
- **その他の言語（上記 5 言語以外: 例 `fr`, `es`, `de`, `pt-BR` など）**:
    - 対象言語のネイティブにとって自然で丁寧な現地表現を使用してください。
    - 単なる直訳を避け、IT・ブラウザ拡張機能分野で一般的に使われる専門用語（拡張機能、ショートカット、タブ、ブックマーク等）へ適切にローカライズしてください。
    - `Short Description` は最大 132 文字以内に収め、下記の全言語共通スタイル制限（`Detailed Description` 本文への Markdown 禁止、現地で視認性の高い記号装飾、客観的・事実ベースの記述）およびセクション 4 のキーワードスパム対策を厳守してください。
- **スタイル制限（全言語共通）**:
    - **Markdown非対応（ストア転記用本文）**: 各 `store_description.<lang>.md` ファイル内の `Name`, `Short Description`, `Detailed Description` などの大見出し（ストアの入力欄に対応する部分）は `### **...**` として残します。しかし、**`Detailed Description` の中身（本文）には一切 Markdown を使用しないでください**。本文内の小見出し（コマンド一覧など）もプレーンテキストにしてください。
    - **視認性のための記号装飾**: プレーンテキスト内での視認性を高めるため、見出しや強調には各言語に適した記号を効果的に使用してください。
        - **英語版**: 全角記号は避け、半角記号（`[ ]`, `-`, `*` など）を使用します（例: `[ CORE FEATURES ]`, `- Feature`）。
        - **日本語版**: 全角記号（`【 】`, `■`, `・` など）を使用します（例: `【 主な機能 】`, `■ 機能`）。
        - **中国語版（簡体字・繁体字）**: 全角記号（`【 】`, `■`, `・` など）を使用します（例: `【 主要功能 】`, `■ 功能`）。
        - **韓国語版**: `[ ]`, `■`, `-`, `•` など韓国語環境で視認性の高い記号を使用します（例: `[ 주요 기능 ]` または `■ 주요 기능`, `- 기능`）。
        - **その他の言語**: 各言語環境で自然かつ視認性の高い記号（欧文圏では `[ ]`, `-`, `*` などの半角記号など）を使用します。
    - **絵文字は最小限に**: 絵文字を多用せず、各セクションの見出し（ 💡 など）程度に留めてください。
    - **「AI的」な表現の禁止**: 「〜してみましょう！」「〜するだけです！」といった、AIが生成したような過度に親近感のある、あるいは煽り気味な表現は避けてください（他言語でも同等の表現を避けてください）。
    - **安易な誇張表現の禁止**: 「爆速」や「爆誕」といった、安易で使い古された誇張表現は避けてください（他言語でも同様の誇張表現を避けてください）。
    - **客観的・事実ベース**: 主観的な表現（例：「最高に便利」「素晴らしい」など）やユーザーへの問いかけは避けて、機能やメリットを客観的事実に基づいて簡潔に記述してください。

### 4. ストアポリシー準拠（キーワードスパム / Yellow Argon 対策）
Chrome ウェブストア等の審査で「キーワード スパム（Keyword Stuffing / Yellow Argon）」として却下されるのを防ぐため、すべての対応言語のメタデータ（`Name`、`Short Description`、`Detailed Description`、および `manifest.json` / `_locales/*/messages.json` の説明文）で以下を厳守してください：

- **外部サービス名・ブランド名の列挙禁止**: 対応サイト・検索ショートカット・プリセットなどを説明する際、サードパーティのサービス名やブランド名（例: `Google, Bing, Yahoo, GitHub, YouTube...` など）を括弧内や箇条書きで並記・列挙しないでください。代わりに「主要な検索エンジンや開発者向けサイトのプリセット」のように機能・カテゴリベースで一般化して記述してください。
- **無関係・過剰なキーワードの禁止**: 検索流入やランキング操作を狙った無関係なキーワード、タグ・ハッシュタグ風の単語リスト、不要な同義語の羅列を含めないでください。
- **同一キーワードの過度な反復禁止**: 特定の単語やフレーズを不自然な頻度で繰り返さず、人間が読んで自然な文章として簡潔に記述してください。

### 5. 権限の使用理由（`store_permissions_justification.md`）
Chrome ウェブストアの「プライバシー（Privacy）」審査タブに入力する権限の使用理由を、`store_permissions_justification.md` としてプロジェクトルートにまとめます。

- **記述言語**: 審査フォームへそのまま転記しやすい **英語（審査提出用）** と、内容確認用の **日本語（確認用）** を 1 ファイル内に併記してください。
- **本文の書式**: ストアの審査入力欄へコピー＆ペーストできるよう、各 `English` / `日本語` セクションの本文は Markdown 装飾を使わないプレーンテキストで記述してください。
- **対象となる権限の網羅**:
  - `manifest.json` に宣言されている `permissions`、`optional_permissions`、`host_permissions`、`optional_host_permissions`、および `content_scripts[].matches` によりホスト権限が発生する対象パターンを漏れなく洗い出してください。
  - 追加権限を一切要求していない場合は、その旨を明記してください。
  - **未使用権限の検出**: `manifest.json` に宣言されているものの、実際のソースコード上で使用されていない権限が見つかった場合は、最小権限の原則（Principle of Least Privilege）に基づき、ユーザーへ不要な権限の削除を提案・警告してください。
- **記載すべき必須項目と記述品質**:
  1. **単一用途の説明 (`Single Purpose Description`)**: 拡張機能の明確で単一の目的を 1〜2 文で簡潔に記述します。
  2. **権限ごとの使用理由 (`Permission Justifications`)**:
     - 各権限について、「どのユーザー向け機能のために」「具体的にどの処理・Chrome API で使用しているか」を実際のソースコードの事実に基づいて記述します。
     - 「拡張機能の動作に必要（Needed for the extension to work）」のような抽象的な記述は審査で却下されるため厳禁です。
     - 広範なホスト権限（例: `<all_urls>`、`https://*/*`）を使用している場合は、なぜ特定のドメイン限定や `activeTab` では実現できないのかも具体的に説明してください。
     - データの外部送信を行わずローカルのみで完結する場合は、その事実も明記してください。
  3. **リモートコードの使用有無 (`Remote Code Usage`)**: 外部ホストされたスクリプトや動的コード実行を使用していないこと（すべてのコードがパッケージ内に同梱されていること）を実装確認のうえ明記します（使用している場合はその理由を正確に記述）。
- **出力フォーマット例**:
  ```markdown
  # Chrome Web Store Permissions Justification

  ## Single Purpose Description

  ### English
  <拡張機能の単一用途を1〜2文で簡潔に記載>

  ### 日本語
  <確認用の日本語訳>

  ## Permission Justifications

  ### `storage`
  #### English
  <具体的な機能・用途・データ保存範囲をプレーンテキストで記載>

  #### 日本語
  <確認用の日本語訳>

  ### Host permissions (`<対象パターン>`)

  <具体的な機能・対象ページでの挙動・より狭い権限で代替できない理由を記載>
  ```

## ワークフロー

1.  **対象言語の判定**: ユーザーから言語の明示指定があるか確認し、指定がない場合は `package/_locales/` を最優先として一般的な `_locales/` 配置を探索します。`messages.json` を含む有効な言語フォルダから対象言語（`_` を `-` に変換した `<lang>`）を決定し、見つからない場合は英語（`en`）・日本語（`ja`）にフォールバックします。
2.  **メタデータと権限の分析**: `manifest.json`、`package.json`、および各 `_locales/*/messages.json` から名前、バージョン、説明文、主要なキーワード、およびすべての要求権限（`permissions` / `optional_permissions` / `host_permissions` / `content_scripts[].matches` 等）を抽出します。
3.  **機能と権限使用箇所の特定**: ソースコード・仕様書・必要に応じて関連する Issue / PR を分析し、拡張機能の主要なセールスポイント（3〜5個）と、各権限が実際に使用されている機能・API を特定します（未使用権限があれば記録します）。
4.  **対象言語ごとのストア説明文ドラフト作成**: ストア説明文を生成対象とする場合、セクション 2・3 の構造と言語要件に従って、判定された各対象言語の `store_description.<lang>.md` を作成します（従来の 5 言語には各言語向け詳細ガイドライン、それ以外の言語には共通品質ガイドラインを適用します）。単なる直訳ではなく、各言語圏のユーザー向けに適切な技術用語でローカライズされていること、`messages.json` と表記が一貫していること、および `Short Description` が各言語で最大 132 文字以内に収まっていることを確認してください。
5.  **権限の使用理由の作成**: 権限使用理由を生成対象とする場合、セクション 5 の構成に従って `store_permissions_justification.md`（英語・日本語併記）を作成・更新します。
6.  **ポリシー・表現チェック**:
    - ストア説明文のすべての対象言語で、外部サービス名・ブランド名の列挙やキーワードの過度な反復（キーワードスパム / Yellow Argon）、および本文への Markdown 混入がないか確認します。
    - `store_permissions_justification.md` で、すべての宣言権限が漏れなく具体的な機能根拠付きで説明されているか、コードと矛盾する記載がないか確認します。
7.  **レビューと保存・更新**: 既存ファイルと比較し、必要に応じて部分的な更新または新規作成を行います。旧形式の `store_description.md` から移行した場合は、旧ファイルの削除可否をユーザーに確認します。また、現在の対象言語に含まれない既存の `store_description.<lang>.md` がある場合は自動削除せず、対象外（未更新）である旨を報告して削除可否をユーザーに確認します。
8.  **変更内容の説明**: 判定した対象言語と探索元の `_locales` パス、作成・更新した各ファイルと変更内容をユーザーに説明し、対象外の既存ファイルや未使用の権限が検出された場合はその確認・削除提案も併せて報告してください。

## 注意事項
- 各言語の説明文ファイル（`store_description.<lang>.md`）および権限使用理由ファイル（`store_permissions_justification.md`）は、すべてプロジェクトのルートに作成してください。
- ユーザーから特定の言語のみ（例：「日本語版だけ更新して」「韓国語のみ作成して」）や権限の使用理由のみ（例：「権限の使用理由だけまとめて」）が明示指定された場合は、`_locales` による自動判定よりユーザー指定を優先し、指定された対象ファイルのみを作成・更新してください。
- 既存ファイルが存在する場合は、内容を完全に上書きするのではなく、必要な部分のみを更新してください。
- 現在の `_locales` 判定結果に含まれない既存の `store_description.<lang>.md` がプロジェクトルートにある場合は、自動で削除せず、対象外（未更新）である旨をユーザーに報告し削除可否を確認してください。
- 旧形式の単一ファイル `store_description.md` が存在する場合は、内容を引き継いで判定された対象言語（見つからない場合は英語・日本語）の言語別ファイルのみを作成したうえで、旧ファイルの削除可否を必ずユーザーに確認してください。
