# Issue 駆動実装スキル (`issue-implementer`)

このスキルは、GitHub の Issue 番号を起点として Issue の内容を精査し、**Spec Kit** のワークフロー（`speckit-specify` → `speckit-plan` → `speckit-task`）に沿って仕様書・実装計画・実装タスクを段階的に作成したうえで、実装・検証・PR（Pull Request）作成までを一貫して進めるためのスキルです。  
仕様上の不明点や、実装にあたってプロジェクト側で合意・決定が必要な事項が見つかった場合は、その内容を整理して対象 Issue にコメントを追加します。

---

## 前提・ツールとワークフローの確認

作業を開始する前に、環境とプロジェクト構成を確認してください。

1. **GitHub Issue / PR 操作手段**:
   - 利用可能な **GitHub MCP ツール**、または **`gh` CLI**（`gh issue view` / `gh issue comment` / `gh pr create`）を使用します。
   - `gh` CLI を使用する場合は、カレントリポジトリが対象 GitHub リポジトリに紐づいていること、および認証済み（`gh auth status`）であることを確認してください。
2. **Spec Kit (`spec-kit`) 環境の確認**:
   - プロジェクト内で利用可能な **`speckit-specify`**、**`speckit-plan`**、**`speckit-task`**（スキル・スラッシュコマンド・プロンプト定義等、名称が `speckit.specify` / `speckit.tasks` 等の表記揺れを含む）の有無を確認します。
   - `.specify/` ディレクトリ（`.specify/memory/constitution.md`、`.specify/templates/`、`.specify/scripts/`）や既存の `specs/` ディレクトリを確認し、プロジェクト固有の憲章（Constitution）や規約を把握します。
   - 定義された `speckit-*` スキルやワークフローが存在する場合は、**必ずそれらの手順・テンプレート・スクリプトに従って**各ステップを実行してください。

---

## 実行手順

### 1. Issue 番号の特定と Issue 内容の取得・確認
1. ユーザーから指定された Issue 番号（例: `#123` / `123`）を確認します。指定されていない場合はユーザーに尋ねてください。
2. Issue の詳細（タイトル、本文、ラベル、ステータス、担当者、**既存の全コメント**、参照リンクや関連 Issue / PR）を取得し、要件・背景・既に行われた議論を漏れなく把握します。
   - 例（`gh` CLI の場合）: `gh issue view <Issue番号> --comments`（または `--json title,body,labels,state,comments`）
3. リポジトリの現在のコードベースや `.specify/memory/constitution.md` を確認し、Issue の内容と現状のアーキテクチャ・仕様との関連性を把握します。
4. 既に対応する作業ブランチや `specs/<NNN-feature-name>/` が存在するか確認してください。デフォルトブランチ（`main` / `master` 等）にいる場合や作業ブランチが未作成の場合は、Spec Kit の規約やプロジェクトのブランチ命名規則に従って作業ブランチを作成・切り替えてから進めます。

### 2. 不明点・決定事項の精査と Issue へのコメント追加
Issue の内容とコードベースを照らし合わせ、以下を精査します。

- 機能要件の境界（どこまでを今回のスコープとするか）
- 入力・出力・エラー処理・エッジケースの挙動
- UI / API / データモデルなど、複数の選択肢があり設計判断が必要な点
- 既存仕様や `.specify/memory/constitution.md` との矛盾・競合

**決めなければならないことや不明点が見つかった場合**:
1. 論点を「不明点／決定事項」「考えられる選択肢（推奨案があれば理由付きで記載）」「実装への影響」に整理します。
2. 対象 Issue に追加するコメントを作成し、**ユーザーへの事前確認（許可）を求めずに**そのまま Issue へコメントを投稿します（投稿後、コメント内容と URL をユーザーへ報告してください）。
   - 例（`gh` CLI の場合）: `gh issue comment <Issue番号> --body "<コメント内容>"`
3. **続行判断**:
   - **ブロッカー（回答がないと仕様や実装方針が定まらない事項）**がある場合は、Issue にコメントを投稿したうえで「回答待ちのため一時停止するか、暫定方針で進めるか」をユーザーに確認してください。
   - **軽微な確認事項・情報共有**であり暫定方針で進めて差し支えない場合は、その方針を明記したうえで次のステップへ進みます。

> **注意**: 以降の `speckit-specify` / `speckit-plan` / `speckit-task` / 実装の**どのフェーズであっても**、新たに決めなければならないことや不明点が判明した場合は、同様に整理して Issue にコメントを追加してください。

### 3. `speckit-specify` による仕様書の作成
1. **`speckit-specify`** を用いて、Issue の要件および既存コメント・決定事項を反映した仕様書（`specs/<NNN-feature-name>/spec.md` 等）を作成します。
2. 仕様書には Issue 番号への参照（例: `Related Issue: #<Issue番号>`）を含め、トレーサビリティを確保します。
3. 仕様書作成中に曖昧な要件や未決定事項が見つかった場合は、ステップ 2 の要領で Issue へのコメント追加を行います。

### 4. `speckit-plan` による実装計画の作成
1. 作成した仕様書（`spec.md`）と `.specify/memory/constitution.md`、および現在のコードベースを基に、**`speckit-plan`** を用いて実装計画（`plan.md`、および必要に応じて `research.md`、`data-model.md`、`contracts/` 等）を作成します。
2. 設計上、プロジェクト全体に影響する技術選定や互換性判断など Issue 上で合意すべき決定事項が出た場合は、Issue にコメントを追加して確認します。

### 5. `speckit-task` による実装タスクの作成
1. `spec.md` と `plan.md` を基に、**`speckit-task`** を用いて実装タスク一覧（`tasks.md`）を作成します。
2. タスクの依存関係・実装順序・テストや検証タスクが漏れなく分解されているか確認します。
3. （推奨）実装に着手する前に、作成した仕様書・実装計画・実装タスクの概要をユーザーへ共有し、実装へ進んでよいか確認してください（ユーザーから一括実行を指示されている場合はそのまま実装へ進みます）。

### 6. タスクに基づく実装と検証
1. `tasks.md` の順序・チェックリストに従ってコードとテストを実装します。
2. 各タスクが完了するごとに、`tasks.md` の該当項目（`- [ ]` → `- [x]`）を適宜更新します。
3. 実装中に仕様書や計画では想定されていなかったエッジケースや仕様不備に遭遇した場合は、独断で仕様を変えず、不明点・決定事項として Issue にコメントを直接投稿し、必要に応じて `spec.md` / `plan.md` / `tasks.md` にも反映します。
4. すべての実装タスク完了後、プロジェクトに存在する検証コマンド（`package.json` の scripts、Makefile、`.github/workflows/` 等の CI 設定を確認し、ユニットテスト・統合テスト・ビルドチェック・型チェック・lint 等）を実行します。
   - 失敗するテストやビルドエラーがある場合は、すべて修正して**全チェックがパスするまで**検証を繰り返してください。

### 7. コミット・プッシュと PR（Pull Request）の作成
1. **前提確認**: プロジェクトに定義されているユニットテストやビルドチェック（および lint・型チェック等）がすべてパスしていることを確認します。未実行または失敗している項目がある場合は PR を作成せず、ステップ 6 に戻って解消してください。
2. デフォルトブランチ以外の作業ブランチ上にいることを確認します（万一デフォルトブランチ上であれば、適切な作業ブランチを作成して切り替えます）。
3. Spec Kit で生成・更新したドキュメントや実装・テストの変更ファイルをステージングし、プロジェクトのコミット規約（または Conventional Commits）に従ってコミットを作成します。
4. 作業ブランチをリモートリポジトリへプッシュします（例: `git push -u origin <ブランチ名>`）。
5. **ユーザーへの事前許可を求めずに**、GitHub MCP ツールまたは `gh pr create` を用いて PR を作成します。
   - プロジェクトに `.github/pull_request_template.md` 等の PR テンプレートがある場合はその構成に従ってください。
   - PR 本文には、対象 Issue の参照（完了している場合は `Closes #<Issue番号>`、Issue 上の確認待ち事項や未確定要素が残っている場合は `Refs #<Issue番号>` として必要に応じて Draft PR `--draft` を検討）、変更内容の概要、作成した Spec Kit ファイル、**実行したテスト・ビルドチェックのコマンドと結果**を明記します。
6. 最終結果をユーザーに報告します（参照した Issue、作成した Spec Kit ファイル一式、追加した Issue コメント、変更・作成したソースファイル、テスト・ビルドチェックの検証結果、**作成した PR の URL**）。

## Issue コメントのテンプレート例

不明点や決定事項を Issue に投稿する際は、読み手が回答しやすいよう以下の構造を目安にしてください（言語は Issue の既存スレッドの言語に合わせて調整してください）。

```markdown
実装を進めるにあたり、以下の点について確認・決定が必要です。

### 1. [確認事項のタイトル]
- **背景 / 不明点**: （仕様・実装上のどの部分が未確定か）
- **選択肢**:
  - A: （案Aの内容・メリット/デメリット）
  - B: （案Bの内容・メリット/デメリット）
- **推奨案**: （エージェントとしての推奨案と理由、または暫定方針）

### 2. [確認事項のタイトル]
...
```

## 厳守事項

- **フェーズの省略禁止**: いきなりソースコードの編集を始めず、必ず「Issue 確認 → `speckit-specify` → `speckit-plan` → `speckit-task` → 実装・検証 → PR 作成」の順序で進めてください。
- **ユニットテスト・ビルドチェックの通過必須**: プロジェクトにユニットテストやビルドチェック（lint・型チェック等を含む）が定義されている場合は、必ずすべて実行してパスさせた上で PR を作成してください。テストやビルドが失敗したまま、または未検証のまま PR を作成することは禁止です。
- **Issue コメント・PR の自動投稿／作成**: 不明点や決定事項の Issue コメント投稿、および実装・検証完了後の PR 作成（作業ブランチのコミット・プッシュ含む）は、ユーザーへ事前許可を求めずに実行し、実行結果（投稿内容や PR の URL）を報告してください。ただし、第三者が読んでも意図が伝わるよう、事実に基づいた丁寧で明確な記述を心がけてください。
- **推測での仕様補完の禁止**: 判断が分かれる仕様や決定事項を勝手に推測して実装を進めないでください。不明点は明示し、Issue コメントおよびユーザーへの確認を行ってください。
- **Git 破壊的操作の禁止**: PR 作成に伴う作業ブランチへのコミット・プッシュ・PR 作成は許可されますが、デフォルトブランチ（`main` / `master` 等）への直接プッシュ、強制プッシュ（`git push --force`）、PR のマージ、Issue の直接クローズなどの操作はユーザーの明示的な指示がない限り実行しないでください。
