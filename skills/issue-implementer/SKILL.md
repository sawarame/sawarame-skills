# Issue 駆動実装スキル (`issue-implementer`)

このスキルは、GitHub の Issue 番号を起点として**ユーザーとの対話や確認待ちを行わずに自律（放置）で動作**し、以下のいずれかのゴールまでを一貫して遂行するためのスキルです。

- **ゴール A（不明点・要決定事項がある場合）**: 推測で実装を進めず、確認が必要な事項を整理して対象 Issue にコメントとして直接登録し、その旨を報告して処理を終了します。
- **ゴール B（実装内容が明瞭な場合）**: 実装に着手する前に**仕様および技術要件を整理して対象 Issue にコメントとして残し**、他の作業に影響を与えないよう **`git worktree`** で隔離した作業環境を作成したうえで、実装・テスト／ビルド検証・PR（Pull Request）作成までを一気通貫で完了します。PR 作成後は作業用 worktree を片付け、**必ず元のブランチ・元の作業状態に戻します**。

> **注**: 本スキルでは Spec Kit（`speckit-specify` / `speckit-plan` / `speckit-task`）は使用しません。仕様や技術要件は Issue コメントとして記録したうえで実装を進めます。

---

## 前提・ツールとプロジェクト規約の確認

作業を開始する前に、環境とプロジェクト構成を確認してください。

1. **GitHub Issue / PR 操作手段（Bot 認証ラッパーの優先使用）**:
   - Issue の確認、Issue コメントの投稿、および PR 作成には、本スキルに同梱されているラッパースクリプト `scripts/gh-as-bot.mjs`（本 `SKILL.md` と同階層配下、通常は `~/.gemini/config/plugins/sawarame-skills/skills/issue-implementer/scripts/gh-as-bot.mjs`）経由で **`gh` CLI** を実行します。
     ```bash
     node ~/.gemini/config/plugins/sawarame-skills/skills/issue-implementer/scripts/gh-as-bot.mjs <ghサブコマンドと引数...>
     ```
   - このラッパーは **`~/.config/github-app/.env` が存在する場合** はその設定（GitHub App ID と `.pem` 秘密鍵）から Installation Access Token を生成して **Bot 名義（`GH_TOKEN`）** で `gh` を実行し、**存在しない場合** は従来通りローカルでログインしている `gh` ユーザーでそのまま実行します。
   - **セキュリティ上の禁止事項**: `~/.config/github-app/.env` や `.pem` 秘密鍵ファイルの中身をエージェントが直接読み取らないでください（認証処理は必ず `gh-as-bot.mjs` 内部で完結させます）。
   - **GitHub MCP ツールの扱い**: GitHub MCP ツールは `~/.config/github-app/.env` の Bot 設定を参照せず個人アカウントで投稿してしまうため、原則使用せず `gh-as-bot.mjs` を使用してください（`~/.config/github-app/.env` が存在せず、かつ `gh` CLI も使用できない環境でのみ代替として使用します）。
   - 事前確認として、カレントリポジトリが対象 GitHub リポジトリに紐づいていること、および `~/.config/github-app/.env` が存在しない場合は `gh auth status` で認証済みであることを確認してください。
2. **プロジェクト規約の確認**:
   - リポジトリ内にコントリビューション規約・開発ガイド・ルール定義（`CONTRIBUTING.md`、`AGENTS.md`、`CLAUDE.md`、`.github/pull_request_template.md` 等）が存在する場合は、設計・実装・テスト・PR 作成においてそれらの規約に従います。

## 実行手順

### 1. Issue 番号の特定・現在状態の記録・Issue 内容の確認
1. 指示された Issue 番号（例: `#123` / `123`）を取得します。Issue 番号が指定されていない場合は、対話による聞き返しは行わず、番号未指定である旨を出力して終了してください。
2. 開始時の**元のリポジトリルートパス**と**元のブランチ名**（`git branch --show-current`）を記録しておきます。元の作業ディレクトリにある未コミット変更やチェックアウト中のブランチには一切手を加えません。
3. Issue の詳細（タイトル、本文、ラベル、ステータス、担当者、**既存の全コメント**、参照リンクや関連 Issue / PR）を取得し、要件・背景・既に行われた議論を漏れなく把握します。
   - 例: `node ~/.gemini/config/plugins/sawarame-skills/skills/issue-implementer/scripts/gh-as-bot.mjs issue view <Issue番号> --comments`（または `--json title,body,labels,state,comments`）
4. リポジトリの現在のコードベースや関連ドキュメントを確認し、Issue の内容と現状のアーキテクチャ・実装との関連性を把握します。

### 2. 不明点・決定事項の精査と分岐判断
Issue の内容（既存コメント含む）とコードベースを照らし合わせ、以下を精査します。

- 機能要件の境界（どこまでを今回のスコープとするか）
- 入力・出力・エラー処理・エッジケースの挙動
- UI / API / データモデルなど、複数の選択肢があり設計判断が必要な点
- 既存仕様やプロジェクト規約との矛盾・競合

**決めなければならないことや不明点が見つかった場合**:
1. 論点を「不明点／決定事項」「考えられる選択肢（推奨案があれば理由付きで記載）」「実装への影響」に整理します。
2. 対象 Issue に追加するコメントを作成し、**ユーザーへの事前確認（許可）を求めずに**そのまま Issue へコメントを投稿します。
   - 例: `node ~/.gemini/config/plugins/sawarame-skills/skills/issue-implementer/scripts/gh-as-bot.mjs issue comment <Issue番号> --body "<コメント内容>"`
3. **終了判断（ゴール A 完了・回答待ちは行わない）**:
   - 仕様や実装方針が確定できない場合は、Issue にコメントを登録した時点で**実装へは進まず処理を終了**し、投稿したコメント内容と Issue URL を最終報告として出力してください。チャット上でユーザーに回答を求めたり、回答待ちのために停止したりしないでください。

**実装内容が十分に明瞭である場合**:
- 余計な確認コメントは投稿せず、ステップ 3 へ進みます。

> **注意**: 以降のステップ 3〜5 の**どのフェーズであっても**、新たに決めなければならないことや不明点が判明した場合は、同様に Issue へコメントを登録し、実装を続行できない場合は（worktree を作成済みであればクリーンアップして元のディレクトリ・元のブランチに戻したうえで）処理を終了・報告してください。

### 3. 実装前の仕様・技術要件の整理と Issue コメント登録
実装に着手する前に、Issue の要件とコードベース調査の結果を踏まえて今回の実装内容を言語化し、**対象 Issue にコメントとして記録**します。

1. 以下の観点を簡潔かつ明確に整理します（テンプレート例を参照）。
   - **仕様・機能要件**: 実装する振る舞い、対象範囲（スコープ）、入力・出力・エラー時の挙動
   - **技術要件・設計方針**: 採用するアプローチ、変更・追加対象となるファイルやモジュール、データ構造・API・依存関係への影響
   - **検証方針**: 追加・更新するテストおよび実行予定のビルド／チェック項目
2. **ユーザーへの事前許可を求めずに**、整理した内容をそのまま対象 Issue にコメントとして投稿します。
   - 例: `node ~/.gemini/config/plugins/sawarame-skills/skills/issue-implementer/scripts/gh-as-bot.mjs issue comment <Issue番号> --body "<仕様・技術要件コメント>"`
3. 投稿後、確認待ちを行わずにステップ 4 へ進みます。

### 4. `git worktree` による隔離された作業環境の構築
元の作業ディレクトリで行われている他の作業（未コミットの変更やチェックアウト中のブランチ）に影響を与えないよう、**`git worktree` を使用して専用の作業ディレクトリと作業ブランチを作成**します。

1. `git fetch origin` 等で最新のベースブランチ（通常はリポジトリのデフォルトブランチ `origin/main` / `origin/master`、またはプロジェクト規約上のベースブランチ）を確認します。
2. プロジェクトの命名規則に従った新しい作業ブランチ名（例: `feat/issue-<Issue番号>-<概要>` や `fix/issue-<Issue番号>-<概要>`。既に該当 Issue 用の作業ブランチが存在する場合はそれを使用）を決定します。
3. 元のリポジトリの作業ツリーや `git status` を汚さないパス（例: リポジトリ親ディレクトリ配下の `../.worktrees/<repo>-issue-<Issue番号>` や、プロジェクトで `.gitignore` 済みの `.worktrees/` 等）に worktree を作成します。
   - 例: `git worktree add -b <作業ブランチ名> <worktreeパス> <ベースブランチ>`
   - ※同じブランチを複数の worktree で同時にチェックアウトすることはできないため、必ず Issue 用の専用ブランチを作成（または指定）してください。
4. **以降のステップ（ステップ 5〜6 の実装・テスト／ビルド検証・コミット・プッシュ・PR 作成）は、すべてこの作成した worktree ディレクトリ内で実行**してください。元の作業ディレクトリ上のファイルは編集しないでください。

### 5. 実装と検証（worktree 内）
1. ステップ 3 で Issue コメントに記録した仕様・技術要件に沿って、worktree ディレクトリ内でコードとテストを実装します。
2. 実装中に想定外のエッジケースや仕様不備に遭遇し、判断が分かれる場合は独断で仕様を変えず、不明点・決定事項として Issue にコメントを直接投稿します（そのまま実装を完了できない場合は PR を作成せず、worktree を整理して元のディレクトリ・元のブランチに戻した上で処理を終了・報告します）。
3. すべての実装完了後、worktree ディレクトリ内でプロジェクトに存在する検証コマンド（`package.json` の scripts、Makefile、`.github/workflows/` 等の CI 設定を確認し、ユニットテスト・統合テスト・ビルドチェック・型チェック・lint 等）を実行します。
   - worktree に依存パッケージ（`node_modules` 等）が未インストールの場合は、テスト・ビルドに必要な依存関係を適切にセットアップ（例: `npm ci`）したうえで実行してください。
   - 失敗するテストやビルドエラーがある場合は、すべて修正して**全チェックがパスするまで**検証を繰り返してください。

### 6. コミット・プッシュ・PR（Pull Request）作成と元のブランチへの復帰
1. **前提確認**: プロジェクトに定義されているユニットテストやビルドチェック（および lint・型チェック等）がすべてパスしていることを確認します。未実行または失敗している項目がある場合は PR を作成せず、ステップ 5 に戻って解消してください。
2. worktree 内がデフォルトブランチ以外の作業ブランチ上であることを確認します。
3. 実装・テストの変更ファイルをステージングし、プロジェクトのコミット規約（または Conventional Commits）に従ってコミットを作成します（`commit-message-generator` の規約を参照可）。
4. 作業ブランチをリモートリポジトリへプッシュします（例: `git push -u origin <ブランチ名>`）。
5. **ユーザーへの事前許可を求めずに**、`gh-as-bot.mjs` 経由で `gh pr create` を実行し通常 PR を作成します（`pr-creator` の規約も参考にしつつ、ステップ 4 で指定したベースブランチを `--base` に明示してください）。
   - 例: `node ~/.gemini/config/plugins/sawarame-skills/skills/issue-implementer/scripts/gh-as-bot.mjs pr create --base "<ベースブランチ>" --head "<作業ブランチ>" --title "<タイトル>" --body "<本文>"`
   - プロジェクトに `.github/pull_request_template.md` 等の PR テンプレートがある場合はその構成に従ってください。
   - PR 本文には、対象 Issue の参照（`Closes #<Issue番号>` 等）、実装内容の概要（ステップ 3 で Issue に記録した仕様・技術要件への言及を含む）、**実行したテスト・ビルドチェックのコマンドと結果**を明記します。
6. **作業用 worktree のクリーンアップと元のブランチへの復帰**:
   - カレントディレクトリをステップ 1 で記録した**元のリポジトリルート**へ戻します。
   - 作成した作業用 worktree を削除してクリーンアップします（例: `git worktree remove <worktreeパス>`、および必要に応じて `git worktree prune`）。※コミット・プッシュ済みであるため安全に削除できます（依存パッケージ等の未追跡ファイルが残っていて削除できない場合は、不要なビルド生成物等を確認して整理したうえで削除してください）。
   - 元のリポジトリルートで `git branch --show-current` を確認し、**必ず開始時の元のブランチに戻っている状態**にしてください（万一ブランチが変わっていた場合は `git checkout <元のブランチ名>` で戻します）。
7. 最終結果をユーザーに報告します（参照した Issue、追加した Issue コメント（仕様・技術要件または不明点）、変更・作成したソースファイル、テスト・ビルドチェックの検証結果、**作成した PR の URL**、および worktree を削除して元のブランチへ戻した旨）。

## Issue コメントのテンプレート例

コメントの言語は Issue の既存スレッドの言語に合わせて調整してください。

### 1. 不明点・要決定事項がある場合（ゴール A）

```markdown
実装を進めるにあたり、以下の点について確認・決定が必要です。

### 1. [確認事項のタイトル]
- **背景 / 不明点**: （仕様・実装上のどの部分が未確定か）
- **選択肢**:
  - A: （案Aの内容・メリット/デメリット）
  - B: （案Bの内容・メリット/デメリット）
- **推奨案**: （エージェントとしての推奨案と理由）
```

### 2. 実装前の仕様・技術要件を記録する場合（ステップ 3）

```markdown
本 Issue の実装に着手するにあたり、以下の仕様および技術要件で進めます。

### 仕様・機能要件
- （満たすべき振る舞い・対象スコープ）
- （エッジケース・エラー時の挙動）

### 技術要件・実装方針
- **方針**: （採用する設計・アプローチ）
- **主な変更対象**: （対象ファイル・モジュール等）
- **影響範囲 / 注意点**: （互換性・依存関係など）

### 検証方針
- （追加・更新するユニットテスト、実行するビルド／lint／型チェック等）
```

## 厳守事項

- **完全非対話（ユーザー確認・回答待ちの禁止）**: 本スキルは放置実行を前提としています。作業途中でユーザーに確認や許可を求めたり、チャット上で回答待ちのために停止したりしないでください。判断できない不明点がある場合は、対象 Issue にコメントを登録して処理を終了してください。
- **Spec Kit 不使用・実装前の仕様／技術要件コメント必須**: 本スキルでは Spec Kit は使用しません。実装内容が明瞭な場合でもいきなりコードを書き始めず、必ず実装前に仕様と技術要件を整理して対象 Issue にコメントとして残してから実装へ進んでください。
- **`git worktree` による作業隔離と元のブランチへの復帰**: 実装および検証は必ず専用の `git worktree` 上で行い、元の作業ディレクトリ（進行中の他作業・未コミット変更）に一切影響を与えないでください。また、PR 作成後（または途中終了時）は作業用 worktree をクリーンアップし、必ず開始時の元のブランチ・元の作業ディレクトリに戻してください。
- **ユニットテスト・ビルドチェックの通過必須**: プロジェクトにユニットテストやビルドチェック（lint・型チェック等を含む）が定義されている場合は、必ずすべて実行してパスさせた上で PR を作成してください。テストやビルドが失敗したまま、または未検証のまま PR を作成することは禁止です。
- **Issue コメント・PR の自動投稿／作成**: 不明点や仕様・技術要件の Issue コメント投稿、および実装・検証完了後の PR 作成（作業ブランチのコミット・プッシュ含む）は、ユーザーへ事前許可を求めずに実行し、実行結果（投稿内容や PR の URL）を最終報告に出力してください。ただし、第三者が読んでも意図が伝わるよう、事実に基づいた丁寧で明確な記述を心がけてください。
- **推測での仕様補完の禁止**: 判断が分かれる仕様や決定事項を勝手に推測して実装を進めないでください。不明点がある場合は対象 Issue へコメントとして登録し、その旨を報告して終了してください。
- **Git 破壊的操作の禁止**: PR 作成に伴う作業ブランチへのコミット・プッシュ・PR 作成は許可されますが、デフォルトブランチ（`main` / `master` 等）への直接プッシュ、強制プッシュ（`git push --force`）、PR のマージ、Issue の直接クローズなどの操作はユーザーの明示的な指示がない限り実行しないでください。
