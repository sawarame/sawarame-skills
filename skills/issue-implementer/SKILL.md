# Issue 駆動実装スキル (`issue-implementer`)

このスキルは、GitHub の Issue 番号を起点として**ユーザーとの対話や確認待ちを行わずに自律（放置）で動作**し、以下のいずれかのゴールまでを一貫して遂行するためのスキルです。

- **ゴール A（不明点・要決定事項がある場合）**: 推測で実装を進めず、確認が必要な事項を整理して対象 Issue にコメントとして直接登録し、その旨を報告して処理を終了します。
- **ゴール B（実装内容が明瞭な場合）**: 他の作業に影響を与えないよう **`git worktree`** で隔離した作業環境を作成し、**Spec Kit** のワークフロー（`speckit-specify` → `speckit-plan` → `speckit-task`）に沿って仕様書・実装計画・実装タスクを順次作成したうえで、実装・テスト／ビルド検証・PR（Pull Request）作成までを一気通貫で完了します。PR 作成後は作業用 worktree を片付け、**必ず元のブランチ・元の作業状態に戻します**。

---

## 前提・ツールとワークフローの確認

作業を開始する前に、環境とプロジェクト構成を確認してください。

1. **GitHub Issue / PR 操作手段**:
   - 利用可能な **GitHub MCP ツール**、または **`gh` CLI**（`gh issue view` / `gh issue comment` / `gh pr create`）を使用します。
   - `gh` CLI を使用する場合は、カレントリポジトリが対象 GitHub リポジトリに紐づいていること、および認証済み（`gh auth status`）であることを確認してください。
2. **Spec Kit (`spec-kit`) 環境の確認**:
   - プロジェクト内で利用可能な **`speckit-specify`**、**`speckit-plan`**、**`speckit-task`**（スキル・スラッシュコマンド・プロンプト定義等、名称が `speckit.specify` / `speckit.tasks` 等の表記揺れを含む）の有無を確認します。
   - `.specify/` ディレクトリ（`.specify/memory/constitution.md`、`.specify/templates/`、`.specify/scripts/`）や既存の `specs/` ディレクトリを確認し、プロジェクト固有の憲章（Constitution）や規約を把握します。
   - 定義された `speckit-*` スキルやワークフローが存在する場合は、**必ずそれらの手順・テンプレート・スクリプトに従って**各ステップを実行してください。

## 実行手順

### 1. Issue 番号の特定・現在状態の記録・Issue 内容の確認
1. 指示された Issue 番号（例: `#123` / `123`）を取得します。Issue 番号が指定されていない場合は、対話による聞き返しは行わず、番号未指定である旨を出力して終了してください。
2. 開始時の**元のリポジトリルートパス**と**元のブランチ名**（`git branch --show-current`）を記録しておきます。元の作業ディレクトリにある未コミット変更やチェックアウト中のブランチには一切手を加えません。
3. Issue の詳細（タイトル、本文、ラベル、ステータス、担当者、**既存の全コメント**、参照リンクや関連 Issue / PR）を取得し、要件・背景・既に行われた議論を漏れなく把握します。
   - 例（`gh` CLI の場合）: `gh issue view <Issue番号> --comments`（または `--json title,body,labels,state,comments`）
4. リポジトリの現在のコードベースや `.specify/memory/constitution.md` を確認し、Issue の内容と現状のアーキテクチャ・仕様との関連性を把握します。

### 2. 不明点・決定事項の精査と Issue へのコメント追加
Issue の内容とコードベースを照らし合わせ、以下を精査します。

- 機能要件の境界（どこまでを今回のスコープとするか）
- 入力・出力・エラー処理・エッジケースの挙動
- UI / API / データモデルなど、複数の選択肢があり設計判断が必要な点
- 既存仕様や `.specify/memory/constitution.md` との矛盾・競合

**決めなければならないことや不明点が見つかった場合**:
1. 論点を「不明点／決定事項」「考えられる選択肢（推奨案があれば理由付きで記載）」「実装への影響」に整理します。
2. 対象 Issue に追加するコメントを作成し、**ユーザーへの事前確認（許可）を求めずに**そのまま Issue へコメントを投稿します。
   - 例（`gh` CLI の場合）: `gh issue comment <Issue番号> --body "<コメント内容>"`
3. **分岐判断（ユーザーへの回答待ちは行わない）**:
   - **仕様や実装方針が確定できず実装へ進めない場合**: Issue にコメントを登録した時点で**実装や Spec Kit の作成へは進まず処理を終了（ゴール A 完了）**し、投稿したコメント内容と Issue URL を最終報告として出力してください。チャット上でユーザーに回答を求めたり、回答待ちのために停止したりしないでください。
   - **すでに Issue 本文・既存コメント・コードベース・規約から実装内容が十分に明瞭である場合**: 余計な確認コメントは投稿せず、そのままステップ 3 以降へ進みます。

> **注意**: 以降の `git worktree` 作成〜`speckit-specify` / `speckit-plan` / `speckit-task` / 実装の**どのフェーズであっても**、新たに決めなければならないことや不明点が判明した場合は、同様に Issue へコメントを登録し、実装を続行できない場合は作成した作業用 worktree をクリーンアップして元のディレクトリ・元のブランチに戻したうえで処理を終了・報告してください。

### 3. `git worktree` による隔離された作業環境の構築
実装内容が明瞭であると判断できたら、元の作業ディレクトリで行われている他の作業（未コミットの変更やチェックアウト中のブランチ）に影響を与えないよう、**`git worktree` を使用して専用の作業ディレクトリと作業ブランチを作成**します。

1. `git fetch origin` 等で最新のベースブランチ（通常はリポジトリのデフォルトブランチ `origin/main` / `origin/master`、またはプロジェクト規約上のベースブランチ）を確認します。
2. Spec Kit やプロジェクトの命名規則に従った新しい作業ブランチ名（例: `feat/issue-<Issue番号>-<概要>` や `<NNN-feature-name>`。既に該当 Issue 用の作業ブランチが存在する場合はそれを使用）を決定します。
3. 元のリポジトリの作業ツリーや `git status` を汚さないパス（例: リポジトリ親ディレクトリ配下の `../.worktrees/<repo>-issue-<Issue番号>` や、プロジェクトで `.gitignore` 済みの `.worktrees/` 等）に worktree を作成します。
   - 例: `git worktree add -b <作業ブランチ名> <worktreeパス> <ベースブランチ>`
   - ※同じブランチを複数の worktree で同時にチェックアウトすることはできないため、必ず Issue 用の専用ブランチを作成（または指定）してください。
4. **以降のステップ（ステップ 4〜8 の Spec Kit 作成・実装・テスト／ビルド検証・コミット・プッシュ・PR 作成）は、すべてこの作成した worktree ディレクトリ内で実行**してください。元の作業ディレクトリ上のファイルは編集しないでください。

### 4. `speckit-specify` による仕様書の作成
1. worktree ディレクトリ内で **`speckit-specify`** を用いて、Issue の要件および既存コメント・決定事項を反映した仕様書（`specs/<NNN-feature-name>/spec.md` 等）を作成します。
2. 仕様書には Issue 番号への参照（例: `Related Issue: #<Issue番号>`）を含め、トレーサビリティを確保します。
3. 仕様書作成中に曖昧な要件や未決定事項が見つかった場合は、ステップ 2 の要領で Issue へコメントを登録し、仕様が確定できない場合は worktree をクリーンアップして元のブランチに戻した上で処理を終了します。

### 5. `speckit-plan` による実装計画の作成
1. 作成した仕様書（`spec.md`）と `.specify/memory/constitution.md`、および現在のコードベースを基に、worktree ディレクトリ内で **`speckit-plan`** を用いて実装計画（`plan.md`、および必要に応じて `research.md`、`data-model.md`、`contracts/` 等）を作成します。
2. 設計上、プロジェクト全体に影響する技術選定や互換性判断など Issue 上で合意すべき決定事項が出た場合は、ステップ 2 の要領で Issue へコメントを登録し、方針が確定できない場合は worktree をクリーンアップして元のブランチに戻した上で処理を終了します。

### 6. `speckit-task` による実装タスクの作成
1. `spec.md` と `plan.md` を基に、worktree ディレクトリ内で **`speckit-task`** を用いて実装タスク一覧（`tasks.md`）を作成します。
2. タスクの依存関係・実装順序・テストや検証タスクが漏れなく分解されているか確認します。
3. タスク作成後、**ユーザーへの確認や承認待ちを挟まずに**、そのままステップ 7 の実装へ進みます。

### 7. タスクに基づく実装と検証（worktree 内）
1. `tasks.md` の順序・チェックリストに従って、worktree ディレクトリ内でコードとテストを実装します。
2. 各タスクが完了するごとに、`tasks.md` の該当項目（`- [ ]` → `- [x]`）を適宜更新します。
3. 実装中に仕様書や計画では想定されていなかったエッジケースや仕様不備に遭遇した場合は、独断で仕様を変えず、不明点・決定事項として Issue にコメントを直接投稿します（そのまま実装を完了できない場合は PR を作成せず、worktree を整理して元のブランチに戻した上で処理を終了・報告します）。
4. すべての実装タスク完了後、worktree ディレクトリ内でプロジェクトに存在する検証コマンド（`package.json` の scripts、Makefile、`.github/workflows/` 等の CI 設定を確認し、ユニットテスト・統合テスト・ビルドチェック・型チェック・lint 等）を実行します。
   - worktree に依存パッケージ（`node_modules` 等）が未インストールの場合は、テスト・ビルドに必要な依存関係を適切にセットアップ（例: `npm ci`）したうえで実行してください。
   - 失敗するテストやビルドエラーがある場合は、すべて修正して**全チェックがパスするまで**検証を繰り返してください。

### 8. コミット・プッシュ・PR（Pull Request）作成と元のブランチへの復帰
1. **前提確認**: プロジェクトに定義されているユニットテストやビルドチェック（および lint・型チェック等）がすべてパスしていることを確認します。未実行または失敗している項目がある場合は PR を作成せず、ステップ 7 に戻って解消してください。
2. worktree 内がデフォルトブランチ以外の作業ブランチ上であることを確認します。
3. Spec Kit で生成・更新したドキュメントや実装・テストの変更ファイルをステージングし、プロジェクトのコミット規約（または Conventional Commits）に従ってコミットを作成します（`commit-message-generator` の規約を参照可）。
4. 作業ブランチをリモートリポジトリへプッシュします（例: `git push -u origin <ブランチ名>`）。
5. **ユーザーへの事前許可を求めずに**、GitHub MCP ツールまたは `gh pr create` を用いて通常 PR を作成します（`pr-creator` の規約も参考にしつつ、ステップ 3 で指定したベースブランチを `--base` に明示してください）。
   - プロジェクトに `.github/pull_request_template.md` 等の PR テンプレートがある場合はその構成に従ってください。
   - PR 本文には、対象 Issue の参照（`Closes #<Issue番号>` 等）、変更内容の概要、作成した Spec Kit ファイル、**実行したテスト・ビルドチェックのコマンドと結果**を明記します。
6. **作業用 worktree のクリーンアップと元のブランチへの復帰**:
   - カレントディレクトリをステップ 1 で記録した**元のリポジトリルート**へ戻します。
   - 作成した作業用 worktree を削除してクリーンアップします（例: `git worktree remove <worktreeパス>`、および必要に応じて `git worktree prune`）。※コミット・プッシュ済みであるため安全に削除できます（依存パッケージ等の未追跡ファイルが残っていて削除できない場合は、不要なビルド生成物等を確認して整理したうえで削除してください）。
   - 元のリポジトリルートで `git branch --show-current` を確認し、**必ず開始時の元のブランチに戻っている状態**にしてください（万一ブランチが変わっていた場合は `git checkout <元のブランチ名>` で戻します）。
7. 最終結果をユーザーに報告します（参照した Issue、作成した Spec Kit ファイル一式、追加した Issue コメント、変更・作成したソースファイル、テスト・ビルドチェックの検証結果、**作成した PR の URL**、および worktree を削除して元のブランチへ戻した旨）。

## Issue コメントのテンプレート例

不明点や決定事項を Issue に投稿する際は、読み手が回答しやすいよう以下の構造を目安にしてください（言語は Issue の既存スレッドの言語に合わせて調整してください）。

```markdown
実装を進めるにあたり、以下の点について確認・決定が必要です。

### 1. [確認事項のタイトル]
- **背景 / 不明点**: （仕様・実装上のどの部分が未確定か）
- **選択肢**:
  - A: （案Aの内容・メリット/デメリット）
  - B: （案Bの内容・メリット/デメリット）
- **推奨案**: （エージェントとしての推奨案と理由、または暫定方針）

### 2. [確認事項のタイトル]
...
```

## 厳守事項

- **完全非対話（ユーザー確認・回答待ちの禁止）**: 本スキルは放置実行を前提としています。作業途中でユーザーに確認や許可を求めたり、チャット上で回答待ちのために停止したりしないでください。`speckit-*` のサブワークフロー内に対話確認を促す指示がある場合でも、明確な場合は確認を省略して進行し、判断できない不明点がある場合はユーザーではなく対象 Issue にコメントを登録して処理を終了してください。
- **`git worktree` による作業隔離と元のブランチへの復帰**: 実装および Spec Kit 関連ファイルの生成は必ず専用の `git worktree` 上で行い、元の作業ディレクトリ（進行中の他作業・未コミット変更）に一切影響を与えないでください。また、PR 作成後（または途中終了時）は作業用 worktree をクリーンアップし、必ず開始時の元のブランチ・元の作業ディレクトリに戻してください。
- **フェーズの省略禁止**: 実装内容が明瞭な場合はいきなりソースコードの編集を始めず、必ず「Issue 確認 → `git worktree` 作成 → `speckit-specify` → `speckit-plan` → `speckit-task` → 実装・検証 → PR 作成 → 元のブランチへ復帰」の順序で進めてください。
- **ユニットテスト・ビルドチェックの通過必須**: プロジェクトにユニットテストやビルドチェック（lint・型チェック等を含む）が定義されている場合は、必ずすべて実行してパスさせた上で PR を作成してください。テストやビルドが失敗したまま、または未検証のまま PR を作成することは禁止です。
- **Issue コメント・PR の自動投稿／作成**: 不明点や決定事項の Issue コメント投稿、および実装・検証完了後の PR 作成（作業ブランチのコミット・プッシュ含む）は、ユーザーへ事前許可を求めずに実行し、実行結果（投稿内容や PR の URL）を最終報告に出力してください。ただし、第三者が読んでも意図が伝わるよう、事実に基づいた丁寧で明確な記述を心がけてください。
- **推測での仕様補完の禁止**: 判断が分かれる仕様や決定事項を勝手に推測して実装を進めないでください。不明点がある場合は対象 Issue へコメントとして登録し、その旨を報告して終了してください。
- **Git 破壊的操作の禁止**: PR 作成に伴う作業ブランチへのコミット・プッシュ・PR 作成は許可されますが、デフォルトブランチ（`main` / `master` 等）への直接プッシュ、強制プッシュ（`git push --force`）、PR のマージ、Issue の直接クローズなどの操作はユーザーの明示的な指示がない限り実行しないでください。
