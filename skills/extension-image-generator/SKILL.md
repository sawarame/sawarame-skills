# Chrome Web Store Multilingual Image Generator

## 概要
このスキルは、Chrome ウェブストア公開に必要な多言語対応のスクリーンショット画像（各言語 1〜5 枚）を、再利用可能な画像生成スクリプトとあわせて効率的に作成・更新するためのスキルです。

- **再利用可能な生成スクリプト（`scripts/`）**: HTML/CSS テンプレートで各言語のスライドを描画し、自動操作ブラウザ（Playwright 等）で指定サイズの画像として書き出す Node.js スクリプトを対象プロジェクトの `scripts/` 配下に保存・更新します。機能追加・UI 変更・言語追加の際にもスクリプトを再実行して容易に再生成できます。
- **多言語ストア画像（`images/`）**: プロジェクト内の `_locales` ディレクトリ（`package/_locales/` を最優先）から自動判定した対応言語（見つからない場合は英語・日本語、ユーザーから明示指定がある場合はその言語）ごとに、Chrome ウェブストアでの縮小表示でも見やすいシンプルかつ大きめの文字設計で統一された 1〜5 枚のスクリーンショット画像（デフォルト `1280x800`・透過なし 24-bit PNG）を対象プロジェクトの `images/` 直下にフラット出力します。

### 出力ファイル一覧
デフォルトでは、対象 Chrome 拡張機能プロジェクトのルート配下に以下のファイルを生成・更新します。

| 種別 | 出力パス・命名規則 | 備考 |
| :--- | :--- | :--- |
| 画像生成スクリプト | `scripts/generate-store-images.mjs`（および必要に応じたテンプレート・文言定義ファイル） | 単体で再実行可能な Node.js スクリプト。サイズ（`1280x800` / `640x400`）や対象言語の切り替えに対応 |
| ストア用スクリーンショット画像 | `images/store-<NN>.<lang>.png` | `images/` 直下にフラット出力。`<NN>` は `01`〜`05` の 2 桁ゼロ埋め、`<lang>` は有効な言語フォルダ名の `_` を `-` に変換した識別子（例: `images/store-01.en.png`、`images/store-01.ja.png`、`images/store-02.zh-CN.png`）。ユーザーから JPEG が明示指定された場合のみ `.jpg` を使用 |

### 対象外（Out of Scope）
以下の成果物は本スキルの対象外です。ユーザーから依頼された場合は対象外である旨を案内するか、該当スキル・別作業として切り分けてください。
- プロモーションタイル画像（小: `440x280`、マーキー: `1400x560`）の生成
- 拡張機能アイコン（`128x128` 等）の生成
- ストア説明文（`store_description.<lang>.md`）および権限使用理由（`store_permissions_justification.md`）の生成・更新（`extension-description-generator` スキルの責務）
- `_locales/*/messages.json` 自体の自動作成・翻訳

## ガイドライン

### 1. 情報の収集と対象言語の自動判定
スライド構成の企画や画像生成スクリプトの作成・更新を行う前に、必ず対象言語の判定とプロジェクト情報の収集を行ってください。

#### 1.0 対象言語の自動判定ルール
対象言語の判定ルールは `extension-description-generator` スキルと統一します。

1. **ユーザーによる明示指定の最優先**:
   - ユーザーから特定の言語が明示的に指定された場合（例: 「日本語と英語だけ生成して」「韓国語を追加して」など）は、`_locales` による自動判定より **ユーザーの指定を優先し、指定された言語のみ** を生成・更新対象としてください。
2. **`_locales` ディレクトリの探索優先順位**:
   - **最優先**: `package/_locales/` を確認します（`extension-skeleton-generator` の標準構成に準拠）。
   - **フォールバック探索**: `package/_locales/` が存在しない場合は、プロジェクト内の一般的な `_locales/` 配置（プロジェクトルート直下の `_locales/`、`public/_locales/`、`src/_locales/` など、`manifest.json` と同じ階層またはパッケージ出力元の `_locales/`）を探索します。
   - **既定のフォールバック**: いずれの場所にも `_locales/` ディレクトリが存在しない、または有効な言語フォルダが 1 つも存在しない場合は、既定のフォールバックとして **英語（`en`）と日本語（`ja`）** の 2 言語を対象とします。
3. **有効な言語フォルダの判定と言語コード表記**:
   - 検出した `_locales/` 直下のサブディレクトリのうち、中に `messages.json` が存在するフォルダのみを有効な対応言語として扱います（`messages.json` のない空フォルダや、`.DS_Store` などの隠しファイル・隠しディレクトリは無視します）。
   - 出力ファイル名に使う言語コード `<lang>` は、フォルダ名のアンダースコア（`_`）をハイフン（`-`）に変換して正規化します。
     - 例: `en` → `en`、`en_US` → `en-US`、`ja` → `ja`、`zh_CN` → `zh-CN`、`zh_TW` → `zh-TW`、`ko` → `ko`、`fr` → `fr`
4. **対象外となった既存画像の扱い**:
   - `_locales` の変更等により現在の対象言語に含まれなくなった既存の画像ファイル（`images/store-*.<lang>.png` 等）が `images/` に残っている場合、**自動で削除しないでください**（ユーザーが特定言語のみ生成・更新を指定した場合を除く）。対象外（未更新）である旨をユーザーに報告し、削除してよいか確認してください。

#### 1.1 収集対象ファイル
- **`manifest.json`**: 拡張機能名、アイコン画像パス、バージョン、ポップアップ／オプションページ／サイドパネル／コンテンツスクリプト／コマンド等の UI・機能構成を確認します。
- **`package.json`**: プロジェクト名、依存関係（`dependencies` / `devDependencies`）、モジュール形式（`"type": "module"` の有無等）、既存スクリプトを確認します。
- **`_locales/*/messages.json`**: 対象言語の判定に加え、各言語の拡張機能名・説明文・UI 文言を読み取り、画像内の名称・用語の表記を統一します。
- **既存の `store_description.<lang>.md`**: 存在する場合は優先的に参照し、ストア説明文とキャッチコピー・主要訴求ポイント・機能表現・トーンを統一します。
- **`src/` や `js/` 等のソースコード・スタイル・アイコン画像**: 実際の UI 構造（HTML/CSS、コンポーネント構成）、配色（ブランドカラー・アクセントカラー）、アイコン資産、主要機能の正確な挙動を把握します。
- **プロジェクトの仕様書（仕様駆動開発フレームワークを含む）**: プロジェクトの目的・ターゲットユーザー・コア価値・差別化ポイントを正確に把握するために確認します。
  - **Spec Kit (`spec-kit`)**: `specs/*/spec.md`、`.specify/memory/constitution.md` など
  - **Kiro / `cc-sdd`**: `.kiro/steering/product.md`、`.kiro/specs/*/requirements.md`・`design.md` など
  - **OpenSpec**: `openspec/specs/` 配下の仕様書、`openspec/changes/` 配下の変更提案など
  - **その他のフレームワーク / 一般的な仕様書**: `SPEC.md`、`docs/spec.md`、`docs/specs/` など
- **GitHub Issue / PR（必要に応じて）**: ローカルの仕様書やコード差分だけでは機能背景や UI 変更の意図が十分に把握できない場合や、ユーザー指示に関連 Issue / PR がある場合は、`gh issue view` / `gh issue list` / `gh pr view` / `gh pr list`（または GitHub MCP ツール）で内容を確認します（取得できない環境ではローカル情報のみで続行してください）。
- **既存の `scripts/` 内の画像生成スクリプトおよび `images/` 内の既存画像**: 既存のデザイン・テンプレート・文言定義・生成済み画像を確認し、既存資産の再利用・差分更新に活用します。

#### 1.2 既存スクリプト・既存画像がある場合と新規作成の場合
- **既存の画像生成スクリプトが `scripts/` に存在する場合**:
  - ゼロから作り直さず、既存のデザインシステム・テンプレート構成・配色を引き継いで差分更新・再生成を行ってください。
  - `git log`、`store_description.<lang>.md`、`_locales/*/messages.json`、ソースコード・仕様書の変更内容を確認し、新機能・UI 変更・言語追加に伴うスライドや文言の差分を反映します。
  - 出力形式やサイズ切り替え等のオプションが不足している場合は、既存構成との互換性を保ちつつ機能拡張します。
- **既存スクリプトが存在しない場合**:
  - 収集した情報に基づき、拡張機能の主要価値と実 UI を的確に伝えるスライド構成（1〜5 枚）とデザインを企画し、`scripts/` 配下に再利用可能な生成スクリプトを新規作成します。

### 2. 画像生成スクリプトの設計仕様（対象プロジェクトの `scripts/`）

#### 2.1 生成方式とファイル構成
- HTML/CSS テンプレートで各言語のスライドを描画し、自動操作ブラウザ（Playwright 等）を用いて指定サイズの画像として書き出す Node.js スクリプトを、対象プロジェクトのルート配下の `scripts/` フォルダに保存します。
  - 基本構成例:
    - `scripts/generate-store-images.mjs`（エントリポイント兼レンダリング・書き出し処理）
    - 必要に応じて、テンプレートや各言語のスライド文言定義を `scripts/store-images/` 等のサブファイル（例: `slides-data.mjs`、`template.mjs`）に分離しても構いません。
- **スクリプト内のコメント・JSDoc は日本語で記述してください。**

#### 2.2 再利用性・保守性の設計指針
- **データとレイアウトの分離**:
  - スライドの HTML/CSS レイアウト定義と、各言語の見出し・サブコピー・UI モックアップ内文言・バッジ表記などのテキストデータを分離し、文言修正・スライド追加・新規言語追加を容易にしてください。
- **実行時オプションによる柔軟な切り替え**:
  - スクリプト単体で再実行可能とし、コマンドライン引数（および環境変数や設定デフォルト値）で以下を切り替えられるようにしてください。
    - **出力サイズ**: デフォルト `1280x800`、オプション指定（例: `--size=640x400` または `--size=1280x800`）で **`640x400`** へ切り替え可能にする。
    - **対象言語の絞り込み**: 未指定時は `_locales` の自動判定結果（見つからない場合は `en`, `ja`）の全対象言語を生成し、オプション指定（例: `--lang=ja,en`）で特定言語のみ再生成できるようにする。
    - **出力形式（任意）**: デフォルトは透過なし 24-bit PNG（`png`）。ユーザーから JPEG 指定がある場合に対応できるよう `--format=png|jpg` をサポートしてもよい。
- **外部ネットワーク非依存（自己完結）**:
  - 拡張機能のアイコンや装飾図形はプロジェクト内のローカルファイル（Base64 Data URI 埋め込み等）やインライン SVG で読み込み、外部 CDN への通信に依存しない構成にしてください。

#### 2.3 実行環境・依存関係への配慮
- **本番依存関係（`dependencies`）を汚さない**:
  - 画像生成に使う自動操作ブラウザ（Playwright 等）や画像処理ツールを、対象拡張機能プロジェクトの `dependencies` には追加しないでください。
- **既存環境・開発用ツールの活用**:
  - まずローカル環境で利用可能なブラウザ（インストール済みの Google Chrome / Chromium 等）や、`package.json` の既存 `devDependencies`、あるいは `npx` 等で追加インストールを最小限に抑えて実行できないか確認します（例: Playwright の `chromium.launch({ channel: 'chrome' })` やローカル Chrome の実行パス指定を活用し、巨大なブラウザバイナリの不要な再ダウンロードを避ける）。
  - プロジェクトの `devDependencies` にツールを追加する場合は、ユーザーへ変更内容を明示し、拡張機能のビルド成果物（`package/` や `package.zip`）に `scripts/` や `images/`、`node_modules/` が混入しないことも確認してください。

### 3. 出力画像の仕様（対象プロジェクトの `images/`）

#### 3.1 出力先とファイル命名規則
- 出力先は対象プロジェクトのルート配下の **`images/` フォルダ直下（フラット配置）** とします（言語ごとのサブフォルダは作成しません）。
- ファイル命名規則は **`store-<NN>.<lang>.png`** とします。
  - `<NN>`: `01`〜`05` の 2 桁ゼロ埋め連番
  - `<lang>`: `_locales` フォルダ名の `_` を `-` に変換した正規化済み言語コード
  - 出力例:
    - `images/store-01.en.png`、`images/store-02.en.png`
    - `images/store-01.ja.png`、`images/store-02.ja.png`
    - `images/store-01.zh-CN.png`、`images/store-01.zh-TW.png`、`images/store-01.ko.png`
  - ユーザーから JPEG 形式が明示指定された場合のみ拡張子を `.jpg`（`images/store-<NN>.<lang>.jpg`）とします。

#### 3.2 サイズと実ピクセル寸法
- **デフォルトサイズ**: **`1280x800`**
- **切り替え可能サイズ**: ユーザー指定やスクリプト引数により **`640x400`** にも切り替えられるようにします。
- **実ピクセル寸法の完全一致**:
  - 出力画像の実ピクセル寸法が指定サイズ（`1280x800` または `640x400`）と 1 ピクセルの誤差もなく一致するようにしてください。
  - Playwright 等のブラウザ設定では `viewport: { width, height }` とあわせて **`deviceScaleFactor: 1`** を必ず明示し、HiDPI 環境で 2 倍サイズ（`2560x1600` 等）にならないようにします。
  - `640x400` を生成する場合は、`1280x800` 基準のレイアウトを `transform: scale(0.5)` やルート基準サイズ（`rem` / ビューポート単位）で崩れなくスケーリングし、文字や UI 要素がはみ出したり極端に潰れたりしないよう配慮してください。

#### 3.3 ファイル形式（透過なし 24-bit PNG）
- **デフォルト形式**: Chrome ウェブストアの審査要件を満たす **透過なし（アルファチャンネルなし）の 24-bit PNG（RGB）** とします（ユーザーから明示指定があった場合のみ JPEG も可）。
- **アルファチャンネル除去の徹底**:
  - 自動操作ブラウザの PNG スクリーンショットは背景を不透明にしても 32-bit RGBA（アルファチャンネル付き）で保存される場合があります。
  - CSS で明確な不透明背景を設定したうえで、書き出し処理または後処理で **アルファチャンネルを含まない 24-bit RGB PNG** に変換してください（例: Node.js での PNG RGB 変換、`sharp` の `.flatten().removeAlpha().png()`、macOS の `sips` / `ffmpeg` / ImageMagick / Python `Pillow` など、実行環境で利用可能な確実な方法を用い、スクリプト内で自動的に 24-bit PNG として完結させるのが望ましい）。

#### 3.4 枚数とスライド構成
- **生成枚数**: **各言語 1〜5 枚（最大 5 枚）** とします。
- **1 スライド 1 メッセージの原則**: 1 枚の画像に複数の機能や長い説明を詰め込まず、「1 枚につき伝える要点は 1 つ」に絞ってください。
- 拡張機能の規模・主要機能・利用シーンに応じて最適な枚数を決定し、**機能がシンプルな場合に無理に 5 枚へ水増ししないでください**。
- 構成例（機能数に応じて 1〜5 枚に調整）:
  - `01`: 拡張機能のコア価値・メイン画面（大きなキャッチコピー＋主役となるメイン UI）
  - `02`: 主要機能 1 の具体的な利用シーン・UI モックアップ（操作イメージやビフォー／アフター）
  - `03`: 主要機能 2・ショートカット・ワークフロー効率化の図解
  - `04`: カスタマイズ設定・オプション画面（代表的な設定項目を抜粋して大きく表示）
  - `05`: ローカル完結／プライバシー配慮・軽量性などの補足メリット（必要に応じて）
- 全言語でスライドの枚数・構成・訴求順序を統一してください。

### 4. デザイン・多言語・ストアポリシー準拠

#### 4.1 Chrome ウェブストア表示に最適化したシンプル＆高視認性デザイン
Chrome ウェブストアの詳細ページでは、`1280x800` で登録した画像もメイン表示では概ね半分程度（幅 `640px` 前後）に縮小され、下部プレビューや一覧ではさらに小さく表示されます。原寸でちょうどよく見える細かい画面設計ではなく、**縮小表示されても一瞬で内容が伝わるシンプルさと大きな文字**を最優先してください。

- **情報量の上限と余白の確保（詰め込み禁止）**:
  - 1 スライドのテキストは原則として **「大きな見出し（1〜2 行）」＋「短い補足文（任意・1〜2 行以内）」** のみに絞ります（必要に応じて短いラベル 1 つまで）。見出しだけで十分に伝わる場合は補足文を省略し、見出しと UI をさらに大きく見せてください。
  - 箇条書きの羅列、3 つ以上の説明カード、装飾目的の細かいバッジ・タグの多用、注釈やフッター文字など、縮小時に潰れて読みにくくなる要素は配置しないでください。
  - スライド外周と要素間に十分な余白（セーフマージン）を確保し、端まで要素を詰め込まない構成にします。
- **大きめの文字サイズ目安（`1280x800` キャンバス基準、`640x400` 出力時は 0.5 倍相当）**:
  - **メイン見出し**: **`56px〜72px`** 程度（太字、行間 `1.15〜1.3`）。半分に縮小されても十分に読める大きさを維持し、文字数は短く簡潔に収めます（目安: 日本語で 10〜20 文字前後、英語で 3〜8 語前後）。
  - **補足文（任意）**: **`26px〜32px`** 程度（行間 `1.4〜1.5`、最大 2 行以内）。
  - **ラベル・注釈（必要な場合のみ）**: 最小でも **`20px〜24px`** 以上を確保し、縮小時に判読困難になる極小文字（`18px` 未満の本文・説明文字など）を避けてください。
  - **コントラスト比の確保**: 文字と背景の明暗差（コントラスト比）を高く保ち、背景装飾やグラデーションに文字を重ねて視認性を落とさないでください。
- **シンプルな基本レイアウトの型**:
  - 原則として以下の 2 パターンを基本とし、拡張機能の UI 形状とスライド内容に合わせて選択します（特殊な UI で当てはめにくい場合も「大きな見出し＋主役の画面 1 点＋広い余白」の原則を維持してください）。
    1. **左右 2 カラム型（標準・推奨）**:
       - 左側（幅 `40%〜45%` 目安）に大きな見出しと短い補足文（必要に応じ拡張機能アイコン）、右側（幅 `50%〜55%` 目安）に UI モックアップを大きく 1 点配置します。
       - ポップアップ型・サイドパネル型・ツールバー操作型の拡張機能や、キャッチコピーと実画面をバランスよく見せたいスライドに適しています。
    2. **上下 2 段型（ワイド UI・比較表示向け）**:
       - 上部（高さ `25%〜30%` 目安）に大きな見出し（＋必要に応じ 1 行の短い補足文）、下部（高さ `65%〜70%` 目安）に横幅を活かした UI モックアップ（オプション画面、Web ページ上の動作画面、シンプルなビフォー／アフター比較など）を大きく配置します。
- **UI モックアップの焦点化と簡略化**:
  - 拡張機能の実際の UI（ポップアップ、オプション画面、コンテキストメニュー、ページ内オーバーレイ等）に忠実でありつつ、**画面全体を縮小して細かく詰め込むのではなく、伝えたい操作・機能部分を大きくクローズアップまたは抜粋して描画**してください。
  - 周囲のブラウザ枠や背景ページは最小限のシンプルな表現に留め、拡張機能本体（主役）がひと目で分かるようにします。
  - モックアップ内の UI テキストやボタンも縮小表示で判別しやすいサイズ感に整え、不要な設定項目やダミー要素を盛り込みすぎないでください。
- **拡張機能のテーマ色に合わせたシンプル配色**:
  - **白やごく淡いニュートラル色、または拡張機能のテーマ色を薄めた淡いトーンの単色背景（もしくはごく控えめなグラデーション）** を基本とし、複雑な背景模様・過剰な装飾図形・強すぎる影などのノイズを避けてください。
  - **暗いテーマ（ダークモード）が主体の拡張機能**の場合は、拡張機能のブランドや実 UI に調和する落ち着いたダーク背景（深いグレー・ネイビー等）＋明るい文字色でのシンプル配色にも対応します。
  - 全体の配色は「背景色＋文字色＋アクセントカラー（1〜2 色）」程度に絞り、全対象言語・全スライドでレイアウト構造、配色、タイポグラフィの階層、アイコン配置を一貫させてください。

#### 4.2 多言語フォント指定とレイアウト崩れ防止
- **言語別フォントスタックと `lang` 属性**:
  - 各言語の HTML レンダリング時に `<html lang="...">` を正しく設定し、各言語に適したフォントファミリーを指定して文字化け（豆腐化）や日中韓の漢字字形混在（中華フォントと日本語フォントの混在など）を防ぎます。
    - 英語・欧文（`en`, `fr`, `de`, `es` 等）: システムのサンセリフ体（`Inter`, `-apple-system`, `BlinkMacSystemFont`, `"Segoe UI"`, `Roboto`, `"Helvetica Neue"`, `sans-serif` 等）
    - 日本語（`ja`）: `"Hiragino Sans"`, `"Hiragino Kaku Gothic ProN"`, `"Noto Sans JP"`, `"Yu Gothic"`, `"Meiryo"`, `sans-serif` 等
    - 中国語・簡体字（`zh-CN`）: `"PingFang SC"`, `"Hiragino Sans GB"`, `"Noto Sans SC"`, `"Microsoft YaHei"`, `sans-serif` 等
    - 中国語・繁体字（`zh-TW`）: `"PingFang TC"`, `"Noto Sans TC"`, `"Microsoft JhengHei"`, `sans-serif` 等
    - 韓国語（`ko`）: `"Apple SD Gothic Neo"`, `"Noto Sans KR"`, `"Malgun Gothic"`, `sans-serif` 等
    - その他の言語: 対象言語のスクリプト（キリル文字、アラビア文字［必要に応じ `dir="rtl"`］、タイ文字等）を正しく描画できるフォントを指定してください。
- **テキスト長差への対応**:
  - 英語や欧州言語は日本語・中国語に比べて文字列が長くなりやすく、ドイツ語などは長い複合語が生じます。全言語で文字切れ・はみ出し・要素の重なりが起きないよう、**フォントサイズを極端に小さくして無理に詰め込むのではなく、文言を短く簡潔に整えることを優先**したうえで、余白の確保と適切な折り返し設定（`overflow-wrap: break-word` 等）を行ってください。
- **自然なローカライズ**:
  - 単なる直訳を避け、各言語圏で一般的な IT・ブラウザ拡張機能用語を使用してください（`extension-description-generator` の言語要件および `_locales/*/messages.json` / `store_description.<lang>.md` と用語を統一）。

#### 4.3 ストアポリシー準拠（`extension-description-generator` と統一）
- **外部ブランド名・サービス名の不要な列挙禁止**: サードパーティのサービス名やブランド名（例: `Google, Bing, GitHub, YouTube...`）を画像内に並記・列挙したり、第三者の商標・ロゴを無断使用したりしないでください。
- **キーワードスパム表現の禁止**: 検索対策を狙った無関係な単語やタグの羅列を画像内に詰め込まないでください。
- **誇張・煽り・AI 的表現の禁止**: 「爆速」「最高に便利」「〜するだけ！」といった過度な誇張・煽り表現や主観的な美辞麗句は避け、拡張機能の実際の機能とメリットを客観的かつ簡潔に伝えてください。

### 5. 生成後の実画像検証（必須）
画像を書き出しただけで完了とせず、必ず以下の技術検証と目視検証を実施してください。

1. **出力ファイル数・命名規則の確認**:
   - `images/` 配下に、判定した全対象言語 × スライド枚数分の `store-<NN>.<lang>.png`（JPEG 指定時は `.jpg`）がフラットに生成されているか確認します。
2. **実ピクセル寸法の確認**:
   - 全出力画像の実ピクセル寸法が指定サイズ（`1280x800` または `640x400`）と完全一致していることをコマンド等で検証します（例: `file images/store-*.png`、`sips -g pixelWidth -g pixelHeight -g hasAlpha images/store-*.png`、または Node.js による PNG IHDR チャンク検査）。
3. **透過有無（24-bit PNG）の確認**:
   - デフォルトの PNG 出力において、全画像がアルファチャンネルを含まない 24-bit PNG（PNG カラータイプ 2: `RGB` / `8-bit/color RGB`、`hasAlpha: no`）であることを確認します。透過が残っていた場合はスクリプトの変換処理を修正して再生成してください。
4. **生成画像の目視確認（画像読み取り・縮小表示時の視認性チェック）**:
   - 生成された画像をファイル読み取りツール等で実際に目視確認し、以下をチェックしてください。
     - **ストア縮小表示での見やすさ**: Chrome ウェブストア上の縮小表示（幅 `640px` 前後のメイン表示やサムネイル一覧）を想定したときに、見出しが一瞬で読める大きさ・コントラストになっているか、文字や UI 要素が小さすぎて潰れていないか
     - **シンプルさと情報量**: 1 スライドに要素や文章を詰め込みすぎていないか、余白が十分に確保されているか、不要な装飾や細かい文字が残っていないか
     - **レイアウトと描画品質**: 文字切れ・枠外へのはみ出し・要素同士の重なりがないか、文字化け（豆腐）や不自然な改行・日中韓の字形混在がないか、UI モックアップやアイコンの配置・余白に不自然な点がないか
   - 複数言語を生成した場合は、文字が長くなりやすい言語（英語・欧文等）および CJK 各言語（`ja`, `zh-CN`, `zh-TW`, `ko` 等）を中心に確認し、問題が見つかった場合（文字が小さい・情報量が多い・崩れがある等）は文言の短縮・要素の削減・文字サイズ拡大・テンプレート調整を行って再生成・再検証を繰り返してください。

## ワークフロー

1. **対象言語と出力条件の確定**:
   - ユーザーからの明示指定（対象言語、サイズ `1280x800` / `640x400`、枚数、画像形式）を確認します。
   - 言語の明示指定がない場合は、`package/_locales/` を最優先として一般的な `_locales/` を探索し、`messages.json` を含む有効な言語フォルダから対象言語（`_` を `-` に変換した `<lang>`）を自動判定します（見つからない場合は `en`・`ja` にフォールバック）。
2. **プロジェクト情報と既存資産の収集**:
   - `manifest.json`、`package.json`、`_locales/*/messages.json`、既存の `store_description.<lang>.md`、`src/`・`js/` 等のソースコード・スタイル・アイコン、プロジェクトの仕様書（Spec Kit / Kiro / OpenSpec / `SPEC.md` / `docs/spec.md` 等）、必要に応じて関連する GitHub Issue / PR、および既存の `scripts/`・`images/` を確認します。
3. **スライド構成・コピー・デザインの設計**:
   - 拡張機能の主要機能と利用価値に基づき、**1 スライド 1 メッセージ**で各言語 1〜5 枚のスライド構成（水増ししない適正枚数）を設計します。
   - Chrome ウェブストアでの縮小表示を前提に、シンプルで大きめの文字サイズ（`1280x800` 基準で見出し `56px〜72px` 程度）、基本レイアウトの型（左右 2 カラム型／上下 2 段型）、焦点を絞った UI モックアップ、拡張機能のテーマ色に合わせたシンプル配色、ストアポリシー準拠の簡潔なコピーと言語別フォント設定を設計します。
   - 既存の `scripts/` 生成スクリプトがある場合は、既存のデザインと構成をベースに差分設計を行います（ユーザーから視認性改善やデザイン見直しの要望がある場合は 4.1 の基準に沿って刷新します）。
4. **画像生成スクリプトの作成・更新（`scripts/`）**:
   - HTML/CSS テンプレート＋自動操作ブラウザ（Playwright 等）で全対象言語の画像を生成でき、サイズ（`1280x800` / `640x400`）や対象言語を切り替え可能な再利用スクリプトを `scripts/` 配下（例: `scripts/generate-store-images.mjs`）に日本語コメント付きで作成・更新します。
   - 対象プロジェクトの `dependencies` を汚さない実行方法を選定し、デフォルト出力が透過なし 24-bit PNG かつ実ピクセル寸法一致（`deviceScaleFactor: 1`）となるように実装します。
5. **スクリプトの実行と画像出力（`images/`）**:
   - 作成したスクリプトを実行し、対象プロジェクトの `images/` 直下へ `store-<NN>.<lang>.png` を一括生成します。
6. **生成画像の検証と修正サイクル**:
   - 出力ファイル数、実ピクセル寸法（`1280x800` または `640x400`）、透過有無（24-bit PNG）、および画像読み取りによる目視確認（ストア縮小表示を想定した文字の大きさ・シンプルさ・余白、文字切れ・レイアウト崩れ・重なり・文字化けチェック）を実施します。
   - 崩れや仕様違反、縮小時の見づらさが見つかった場合は、文言の短縮・要素の整理・文字サイズ拡大・CSS 修正を行い、問題が解消するまで再生成・再検証を繰り返します。
7. **対象外の既存画像チェックと結果報告**:
   - `images/` 配下に現在の対象言語に含まれない既存画像ファイルが残っている場合は自動削除せず、対象外（未更新）である旨をリストアップして削除可否をユーザーに確認します。
   - 判定した対象言語と探索元の `_locales` パス、作成・更新したスクリプトのパスと再実行コマンド例、生成した画像ファイル一覧、およびサイズ・透過・目視検証の結果をユーザーに分かりやすく報告します。

## 注意事項
- 生成スクリプトは対象プロジェクトのルート配下の `scripts/`、出力画像は対象プロジェクトのルート配下の `images/` 直下（フラット構成）に配置してください。
- ユーザーから特定の言語・サイズ（`640x400` 等）・枚数・形式（JPEG 等）が明示指定された場合は、デフォルト設定や `_locales` 自動判定よりユーザーの指定を優先してください。
- 既存の画像生成スクリプトが `scripts/` に存在する場合は、ゼロから作り直さず既存のデザイン・構成を活かして差分更新してください。
- `_locales` の変更等により対象外となった既存画像が `images/` に残っている場合、ユーザーの承認なく自動削除せず、対象外である旨を報告して削除可否を確認してください。
- 対象拡張機能プロジェクトの `dependencies`（本番依存関係）を汚さないようにし、`scripts/` や `images/` が拡張機能の配布パッケージ（`package/` や `package.zip`）に誤って含まれないように配慮してください。
- プロモーションタイル、拡張機能アイコン、ストア説明文・権限使用理由、`_locales/*/messages.json` の自動作成・翻訳は本スキルの対象外です。

## 例

### スキルの起動
- 「現在のプロジェクトの `_locales` 構成と `store_description` に合わせて、Chrome ウェブストア用の多言語スクリーンショット画像を生成して」
- 「`package/_locales/` に対応する全言語分のストア画像を `1280x800` で作成して、後から再生成できるスクリプトも `scripts/` に残して」
- 「新機能の UI を反映して、既存の画像生成スクリプトを更新して日本語と英語のストア画像を再生成して」
- 「Chrome ウェブストア用に `640x400` サイズで韓国語のスクリーンショット画像を追加生成して」
