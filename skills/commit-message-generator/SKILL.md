# コミットメッセージ生成スキル

このスキルは、ステージされた変更（`git add` されたファイルの差分）を解析し、Conventional Commitsのフォーマットに従った日本語のコミットメッセージを自動生成するためのものです。エージェントは以下の手順で動作します。

## 手順
  1. `git diff --staged` を実行して差分を読み取ってください。
  2. 差分がない場合は「Stagedされた変更がありません」と伝えて終了してください。
  3. プロジェクト内で仕様駆動開発（SDD）フレームワークや仕様書が使用されている場合は、必要に応じて変更箇所に関連する仕様・規約ドキュメントを確認し、変更の意図や背景を把握してください（後述の「仕様駆動開発（SDD）フレームワーク利用時の対応」を参照）。
  4. 差分から、Conventional Commits（またはプロジェクト規約）に沿った簡潔な日本語のコミットメッセージを作成してください。
  5. 最後に `git commit -m "生成したメッセージ"` を実行するかどうか、ユーザーに確認してください。ユーザーに確認する方法は、ユーザーに選択肢を提示して選んでもらう方法でお願いします。


## 仕様駆動開発（SDD）フレームワーク利用時の対応
プロジェクト内で **Spec Kit** やその他の**仕様駆動開発フレームワーク**が使用されている場合は、以下のドキュメントを適宜参照してコミットメッセージの精度と一貫性を高めてください。

- **Spec Kit (`spec-kit`)**: `.specify/memory/constitution.md`（コミット規約の確認）および変更対象に対応する `specs/<NNN-feature-name>/` 配下の `spec.md`、`plan.md`、`tasks.md`
- **Kiro / `cc-sdd`**: `.kiro/steering/`（`tech.md` 等の規約確認）および `.kiro/specs/<機能名>/` 配下の `requirements.md`、`design.md`、`tasks.md`
- **OpenSpec**: `openspec/specs/` および `openspec/changes/<変更提案ID>/` 配下の `proposal.md`、`tasks.md`
- **その他のフレームワーク / 一般的な仕様書**: 各フレームワークの仕様ディレクトリ、または `SPEC.md`、`docs/spec.md` など

- フレームワークの規約ファイルにコミットメッセージのフォーマットや `scope` の指定がある場合はそれを優先してください。
- 仕様書や設計・タスクファイル自体の追加・更新がステージされている場合は、`docs`（またはプロジェクト規約に沿った `type` / `scope`）として適切にメッセージを生成してください。


## 厳守事項
- コミットメッセージは必ずユーザーがステージした変更内容に基づいて生成してください。勝手に`git add`を行い、差分を変更することは絶対にしないでください。
- `git commit` は必ずユーザーの確認を得た後にのみ実行してください。
- `git push` はこのスキルの範囲外です。コミット後の操作はユーザーに任せてください。

## Conventional Commits フォーマット
Conventional Commitsは、コミットメッセージの一貫性を保つための規約で、以下のようなフォーマットを使用します。
```
<type>[optional scope]: <description>
[optional body]
[optional footer(s)]
``` 

### type
コミットの種類を表すキーワードで、以下のいずれかを使用
- `feat`: 新機能の追加
- `fix`: バグ修正
- `docs`: ドキュメントの変更
- `style`: コードの意味に影響を与えない変更（フォーマット、スペース、セミコロンの追加など）
- `refactor`: リファクタリング（機能追加やバグ修正を含まないコードの変更）
- `perf`: パフォーマンスの改善
- `test`: テストの追加や修正
- `chore`: その他の変更（ビルドプロセスやドキュメント生成など）
